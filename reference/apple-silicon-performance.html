Before-show checklist

Apple Silicon performance

Earshot's macOS build uses the shared, Core ML-capable sherpa-onnx / ONNX Runtime libraries. The previous static runtime explicitly disabled Core ML. Both dylibs are included in the app's Frameworks directory; development binaries and tests resolve their copies beside the executable. Windows and Linux retain the static speech runtime.

Enabling an execution provider does not mean every operator runs on the GPU or Neural Engine. Unsupported operations can remain on CPU. Core ML performance also depends on model shapes and conversion. See ONNX Runtime's Core ML documentation.

Defaults and scheduling​

  • Transcription: CPU, with one cached recognizer per model, shared across decode workers. Live decode workers use macOS User Initiated QoS. Keep the existing worker budget for many simultaneous channels; isolated single-line results do not establish the best many-channel setting.
  • VAD: one CPU thread. Its small, frequent windows were faster on CPU in the local probe.
  • Voice recognition: up to four native CPU threads on Apple Silicon, on a supporting-work thread. Automatic discovery reuses the identification embedding. FFT plans, spectral interpolation tables and mel weights are cached across lines; per-frame FFT scratch is reused. An initial coarse turn check avoids dense overlapping windows when the voice strongly agrees throughout.
  • Overlapping speech: native ONNX Runtime on Apple Silicon, with four CPU threads by default. Model preparation happens in the background. Only one separation runs at a time; other lines keep normal transcription while it is preparing or occupied. The portable interpreter remains available on other platforms but is not proven suitable for live use.
  • Translation: the existing Apple Accelerate / Ruy build and INT8 compute remain in place. Translation work and voice identification use supporting-work QoS, while transcription has higher scheduling priority. QoS is restored when a reused blocking-pool thread returns. Translation concurrency stays bounded. Translation speed was not remeasured in this pass.

The scheduler and its threads do not pin work to particular cores. macOS chooses cores using these QoS hints. The defaults preserve CPU execution where it won the installed-model measurements. Core ML remains available for component-specific experiments.

Local measurements​

Measured on the development Apple M3 Pro, 12 CPU cores (6 performance and 6 efficiency), 18 GB RAM, on 19 November 2026. Each row uses a four-second, 16 kHz mono synthetic recording from fixtures/audio/showcaller.wav. Times are medians of five warmed runs. VAD time covers all 125 windows, not one window. Core ML rows include its CPU fallback operations.

Parakeet produced the same text in those three runs. This is a small diagnostic, not a transcript accuracy evaluation or a guarantee for other M-series chips. Initial Core ML model preparation was slower than CPU loading. Early trials performed during compilation were discarded from this table.

The standalone four-second CMN diagnostic measured about 5.3 ms after caching and scratch reuse. The spectral-table test checks every cached interpolation value against the original calculation. The real-model turn probe found the known 3 s and 6 s changes exactly in the three-turn synthetic recording. These tests do not establish accuracy with real crew or comms noise.

A 16-channel, 20-second simulator run with the real models and the default 8 workers × 1 ONNX thread published 72 speech finals, with no decode failures and no channels Behind. Final-text latency was 839 ms median and 1,238 ms p95; first text appeared after 790 ms median measured from the segment start including pre-roll. Process CPU averaged 700% of one core (58% of the 12-core machine), with about 1.23 GB resident memory. This is a short local fixture run, not venue validation.

Repeat the probes​

Run from the repository root with the installed models directory:

cargo run --release -p earshot-speech --example apple_runtime_probe -- /path/to/models cpu 1
cargo run --release -p earshot-speech --example apple_runtime_probe -- /path/to/models cpu 4
cargo run --release -p earshot-speech --example apple_runtime_probe -- /path/to/models coreml 1
EARSHOT_MODELS=/path/to/models cargo test --release -p earshot-speech consecutive_unregistered_fixture_voices_have_turn_boundaries -- --ignored --nocapture
cargo test --release -p earshot-speech normalisation_cost -- --ignored --nocapture

Run benchmarks separately from builds and other model probes. Use examples/loadtest.rs for channel throughput before changing the default worker plan.

The EARSHOT_STT_PROVIDER, EARSHOT_VOICE_PROVIDER, EARSHOT_VAD_PROVIDER, and EARSHOT_SEPARATION_PROVIDER environment variables accept cpu or coreml on Apple Silicon. EARSHOT_ONNX_PROVIDER is the fallback for components without an override. These are development controls; macOS Finder launches do not automatically inherit a terminal's environment. Restart the host after changing a provider. EARSHOT_SEPARATION_THREADS accepts 1–8. An optional EARSHOT_ONNXRUNTIME_LIB points separation at an explicit compatible runtime dylib.

The native separation Core ML path uses fixed input shapes and MLProgram format, and caches compiled models beside the installed ONNX file in .coreml-cache. MLProgram requires macOS 12 or newer. The normal CPU path retains the app's macOS 11 requirement. Core ML compilation can consume substantial time and memory; it is experimental and is not the default.

Overlap trial​

The MossFormer2 model is a pinned 245 MB ONNX conversion of Alibaba's two-speaker model. Its input is a fixed four-second window. Adjacent windows are aligned by their overlap before being blended, since output speaker order can change between windows. Isolated tracks are then split using the channel’s pause policy and sorted by onset, so an A–B–A conversation keeps three turns and text cannot join across long gaps on one voice’s track. Very faint regions relative to that track’s own voice are rejected to reduce cross-speaker bleed; unusually quiet utterances can also be missed.

cargo run --release -p earshot-speech --example overlap_probe -- /path/to/models /path/to/mossformer2_ss_16k.onnx /tmp/earshot-overlap-trial

The isolated CPU run took 8.6 seconds to separate four seconds of audio, with roughly 1.7 GB maximum resident memory for the full probe (including transcription). A Core ML MLProgram trial loaded in about 80 seconds but did not finish within the 90-second test budget. It remains opt-in. Overlap separation is therefore not yet real time on this Mac; leave it off for normal low-latency operation.

This mixes the two repository fixtures at equal RMS, writes the mixture and two isolated WAVs, reports scale-invariant signal-to-distortion improvement, and transcribes all three. One synthetic trial recovered both phrases, with about 22 dB improvement for each source; the mixture produced no transcript in that run. That establishes recovery on this fixture, not real-show reliability. More than two simultaneous speakers, duplicate speech and similar voices remain limitations. Check the isolated runtime and memory results before using separation live.
