OSC input

OSC input lets a lighting desk, a show controller or an app send messages to Earshot: to make the show Safe, to trigger an automation, to add a marker, or (at the highest level, over TCP) to arm.

OSC carries no sign-in. Earshot decides what a message may do by where it came from and by the level you choose here.

Open Setup, then Show control. Only admins can.

Show control in the mock show. It is not a real show. The mock show uses UDP port 53000; a new show uses 4781.

warning

OSC input has been tried only in automated tests against stand-ins on one Mac. No real console has been connected. See Limits and known behaviour.

Turn it on​

OSC input is off by default. While it is off there is no listener at all. No OSC message does anything, not even Make safe. The screen says "OSC input is off, so no device can control Earshot by OSC — not even to make it Safe."

  1. Under Controllers, turn on Controllers may send OSC to Earshot. Its hint reads "Lighting desks, show controllers and apps can send Earshot OSC messages. What they may do is set below."
  2. If the level is already above Make safe only, Earshot asks "Switch on OSC control?" first and says what listed devices will be able to do. Press Switch on OSC control to confirm.
  3. Set the ports (below) and press Save ports.

Once it is on, the screen says "When OSC input is on, any device can make the show Safe."

Ports​

SettingDefaultNotes
UDP port4781What most devices send.
TCP port (optional)EmptyEmpty means TCP is off. It cannot be the same as the web port (4780): the screen says "TCP port: That is the port the web app uses. Choose another."
  • Type the ports, then press Save ports. Until you do, the screen says "Not saved yet." Afterwards it says "Ports saved."
  • A port is a whole number from 1 to 65535.
  • The screen's own hint: "UDP is what most devices send. Arming works only over TCP, and a TCP sender's address cannot be faked. Leave the TCP port empty to switch TCP off."
  • TCP uses SLIP framing (OSC 1.1). Most consoles call this "TCP (SLIP)" or "OSC 1.1". The older "length prefix" TCP style (OSC 1.0) is not accepted.

Which network address it listens on. OSC listens only on the network address the show is set to (all of this computer's addresses by default). If that address is not a usable IP address, or a port cannot be opened, OSC input stays off and an alert says why. It never falls back to listening everywhere.

tip

Use the lowest level that does the job. A desk that only needs a panic button needs Make safe only. A desk that fires Earshot automations needs Trigger automations. Very few shows need Full control.

Devices allowed to control​

The mock show with OSC input switched on, Trigger automations in use and one device allowed. The mock's UDP port reads 53000; a real host starts at 4781. Not a real show.

Under Devices allowed to control the screen says "This computer and these devices can do more than make the show Safe. Use each device's IP address."

  • The list starts empty, shown as "Only this computer".
  • Type an address under Add a device (for example 192.168.1.40) and add it. Earshot asks "Let 192.168.1.40 control Earshot?" and says "That device will be able to trigger automations. OSC has no sign-in, so anything using that address can." (the middle of the sentence follows the level in force). Press Add device.
  • One IP address per device. No ranges, no wildcards, no names, no port. The screen tells you which rule you broke, for example "Type one address, not a range. Add each device on its own." or "Host names are not accepted. Type the device's IP address, like 192.168.1.40."
  • IPv4 and IPv6 addresses are both accepted. The list holds at most 64 devices.
  • To take a device off, press the bin next to its address.

"This computer" always counts as allowed. That is safe because the operating system does not accept a packet with a loopback address (127.0.0.1 or ::1) from the network. macOS, Linux and Windows all drop such packets.

The list matters only above Make safe only. At Make safe only, nobody can trigger anything, listed or not, and that includes this computer.

Make Safe works from anywhere​

Make Safe works from any device, over UDP or TCP, whatever the level, as long as OSC input is on. So do ping and version. The device does not have to be on the list.

There are two ways to send it:

/earshot/armed/off
/earshot/armed  false        (or the number 0, or the string "off")

See OSC examples for how to send them.

Arming works only over TCP​

Arming by OSC works only over TCP, never UDP.

A UDP sender's address can be faked by anyone on the same network. A list of allowed devices therefore cannot protect arming over UDP: anyone could pretend to be your console. A TCP connection has to be answered by the real device, so its address cannot be faked the same way.

To arm by OSC you need all four of these:

  1. OSC input switched on.
  2. The level set to Full control, including arming.
  3. A TCP port set and saved.
  4. The sending device on the Devices allowed to control list (or it is this computer), and connected by TCP.

If the TCP port is empty, nobody can arm by OSC. Activity says so ("Arming by OSC needs the TCP port").

At the Trigger automations level, UDP is allowed from listed devices, but remember that a UDP sender can be forged. Use TCP for anything that matters.

Safe always wins​

Arm and Safe take effect the moment they arrive, in the order they arrive. They are never queued behind other messages, so an Arm followed by a Safe always ends Safe. OSC, the app and the API share one order: a Safe from any of them beats an Arm from any of them that was received earlier.

Other controls wait in a short queue. Making the show Safe empties that queue. A control that arrived before the Safe never runs after it, even if the show is armed again in the meantime. An automation trigger that arrived while the show was Safe runs as a dry run: nothing is sent.

Inside one packet:

  • A Safe anywhere in a packet or bundle, at any depth, is applied even if the rest of the packet is refused: too many messages, nested too deep, timed too far ahead, next to a bad address, from a sender over its limit or not allowed. Only a packet over the size limit is not looked into.
  • A damaged bundle (one that cannot be read as OSC) that visibly contains a make-Safe message still makes the show Safe. Earshot looks for the exact Safe message inside it. Nothing else in a damaged bundle is ever acted on.
  • Only damaged bundles are searched this way. A single damaged message that is not in a bundle is ignored. A packet or TCP frame over 8 KiB is refused unread (on TCP, the connection is closed), so a Safe inside either is not applied. Send Safe as a small, plain message.
  • A packet that contains a Safe never arms. Every Arm in the same packet is ignored, in any order and at any depth. Activity says "Arm ignored: the same OSC packet also made the show Safe". Send Arm and Safe as separate packets (or separate frames on one TCP connection) if you mean both: they are then applied in the order they arrive.
  • If a bundle contains a Safe, any automation trigger in it runs as a dry run.

While Earshot is shutting down, nothing fires and the show cannot be armed.

danger

Safe stops what Earshot would send next. It cannot recall anything that has already left this computer. See Safe and Armed.

Changing OSC input (off, ports, level, allowed devices) closes every open connection and restarts the listener. Every message is checked against the settings in force when it arrives.

TCP connections​

  • A connection must start with an OSC message or bundle. If its first bytes look like a web request (GET, POST and so on) or a secure-connection hello, it is closed at once and nothing in it is acted on. This stops a web page in a browser on the host computer from posting OSC to the port. Activity says "a TCP connection that does not speak OSC (HTTP or TLS?) was closed".
  • The first frame that is not a well-formed SLIP-framed OSC message or bundle (it must start with / or #bundle), or is over 8 KiB, closes the connection. Nothing after it is read.
  • A connection idle for 60 seconds is closed. Send a /earshot/ping now and then to keep one open.
  • At most 32 connections are open at once.

Replies and errors​

  • Replies go back to the sender, under /earshot/reply/.... On UDP they go to the address and port the message came from, so the sending program must listen on the port it sends from. On TCP they come back over the same connection.
  • Errors come back as /earshot/error with two strings: the address received and the reason. For example, /earshot/nonsense is answered /earshot/error "/earshot/nonsense" "unknown Earshot OSC command".
  • Errors are sent only to senders allowed to control.
  • Earshot never answers anything under /earshot/reply or /earshot/error, never replies to a multicast address or to its own port, and sends at most 10 replies a second to one destination. Two Earshot computers therefore cannot ping-pong.

Only three addresses reply at all: /earshot/ping, /earshot/version and /earshot/automation/list. See OSC addresses.

Runaway automations​

An automation fired by OSC or a web request (and anything it chains) that really fires more than 20 times in 10 seconds is stopped. An alert reads "'Name' fired 20 times in 10 seconds and was stopped". It stays stopped until the show is made Safe and armed again, or the automation is edited.

  • This is aimed at loops, for example a console that echoes OSC back into Earshot.
  • Any two firings of one automation from anything other than speech are at least 0.1 seconds apart.
  • MIDI and speech are exempt from the stop. See MIDI for what that means for a MIDI feedback loop.

See When an automation is not running.
