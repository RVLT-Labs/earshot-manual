HTTP API

Everything the Earshot screens do, they do through a web API on the host. A script, a show-control tool or another service can use the same API: read the transcript, follow it live, send a typed line, drop a marker, make the show Safe, run an automation.

This page is a guided tour with examples. The full reference is on the host itself, described next.

The API reference on the host​

Open Setup, then Show control, and press API reference at the top right. It opens /docs on the host in a new tab (for example http://192.168.1.20:4780/docs). On a phone it is under More.

The API reference served by a demo host on one computer. It is not a real show.

It has:

  • A Safety box (Safe always wins; arming is a deliberate act; automations fire only when Armed).
  • Every route, grouped by task: Transcript, Typing and markers, Automations and Armed/Safe, Show setup, Access, History and export, System. Each has the role it needs and a curl example with this host's own address filled in.
  • A walk-through of the live WebSocket connection.
  • The OSC address list.
  • Download openapi.json, the same description as an OpenAPI 3.1 document, for tools that read one.

The page asks you to sign in to Earshot in that browser first, unless the show is Open. It reads the sign-in the Earshot web app keeps in that browser. Opening /docs with a token on the end of the address does nothing: the page accepts no credential of its own.

The basics​

Base addresshttp://<host>:4780/api/v1
BodiesJSON, in and out
Errors{"error": {"code": "...", "message": "..."}} with the matching HTTP status
EncryptionNone in this build. Earshot serves plain http. See Limits and known behaviour.

The examples below use these two lines. Set them once in your shell.

export EARSHOT=http://192.168.1.20:4780
export EARSHOT_TOKEN="paste-your-token-here"

Use the address from Setup, Access, Address for the crew. Do not make up a name for the computer: see "The address must be one the host recognises" below.

Signing in​

Send your token in a header:

Authorization: Bearer <token>

Every route also accepts ?token=<token> on the end of the address, but that is meant for the WebSocket and the event stream, where a browser cannot set a header. Prefer the header: addresses end up in browser history and in logs. Never put a real token in a script you share. Read it from an environment variable, as these examples do.

Where a token comes from

TokenHow to get itRole
The admin tokenearshotd prints it at start, in the Admin: address (the part after ?token=). Set your own with --admin-token. See earshotd.Admin
A personal linkSetup, Access, New personal link. The token is the part of the link after ?token=. It is shown once. See Invites and personal links.Viewer or Operator, as you chose
A password sessionPOST /auth/login with the show password (example below). It is forgotten when the host restarts, and expires after 12 hours without use.Operator

What you are without a token depends on who can connect (Setup, Access):

ModeWith no tokenWith a token
OpenOperatorIts own role, but at least Operator
PasswordRefused (401)A password session is an Operator. A personal link keeps its role.
Personal linksRefused (401)The role the link was made with

So in an Open show you can leave the Authorization header out of every example on this page.

Roles. Reading and typing need Viewer. Live operation (Safe and Armed, running automations, markers, pausing a channel) needs Operator. Changing the show and managing access need Admin. See Roles.

Check what you are:

curl -sS \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/auth/whoami"
{"credential":"open","mode":"open","name":"Guest","role":"operator","token_id":null}

Sign in with the show password, to get a session token:

curl -sS \
  -X POST \
  -H "Content-Type: application/json" \
  -d '{"password":"the show password"}' \
  "$EARSHOT/api/v1/auth/login"

The reply is {"token":"...","role":"operator"}. Use that token as $EARSHOT_TOKEN.

Is the host there?​

These two need no token in any mode.

curl -sS "$EARSHOT/api/v1/health"
{"name":"Earshot","ok":true,"version":"0.1.0"}
curl -sS "$EARSHOT/api/v1/auth/mode"
{"mode":"open","name":"FOH Rack","version":"0.1.0"}

name is the Name shown to others from Setup, Access, or the computer's own name if that is empty. (The name in this example was changed.)

Read everything in one go​

curl -sS \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/state"

The reply is one large object: the show (channels, groups, automations, settings, with secrets hidden), the current session, whether the show is armed, each channel's status, open alerts, and any automations that are not running. It is the place to look up the ids the other calls need:

  • show.channels[].id for a channel,
  • show.automations[].id for an automation,
  • session.id for the current session.

Read the transcript​

Lines of the current session, oldest first:

curl -sS \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/utterances?limit=20"

Only some channels (ids, separated by commas):

curl -sS \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/utterances?channels=01JC8Z4M2Q7K9R3VX5TB6N1WDE&limit=20"

One line looks like this (the list of single words is cut short here):

{
  "id": "01M7H1QYCAN2VNFFGPXTJMHGB8",
  "session_id": "01M7H1EDP38RJNA0R63AQPMZZP",
  "channel_id": "demo-video",
  "started_at": 1794794846602,
  "ended_at": 1794794849012,
  "text": "Recording paused for the interval.",
  "raw_text": null,
  "words": [{"text": "Recording", "confidence": 0.976672, "t0_ms": 181, "t1_ms": 666}],
  "language": "en",
  "speaker_id": null,
  "kind": "speech",
  "author": null,
  "keyword_hits": [],
  "has_clip": false,
  "latency_ms": 491,
  "confidence": 0.95143384,
  "translations": {}
}
  • Times are milliseconds since 1970 (UTC).
  • kind is speech, typed or system.
  • raw_text is what the recogniser heard before the glossary, number tidying and the profanity filter changed it. It is null when nothing was changed, and always null for anyone below Operator.
  • limit is 200 unless you say otherwise, and at most 1000. You get the newest lines that fit, still listed oldest first.
  • Other query options: session= (a session id; the current one if left out), and before= or after= with a line's id, to page backwards or forwards from that line.

Past sessions, newest first:

curl -sS \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/sessions"

Search​

curl -sS \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/search?q=cue%20twelve&limit=10"

Add &session=<id> to search one session. Without it, every session is searched.

Export a session​

format is txt, csv, json or srt. Without session= it is the current session. channels=a,b keeps only those channels.

curl -sS -o transcript.srt \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/export?format=srt"

The start of an SRT export from the demo host:

1
00:00:00,506 --> 00:00:05,433
SM Desk: Good evening all, this is your five minute call for beginners.

2
00:00:04,205 --> 00:00:07,563
ASM Stage Left: Stage left copies, all cast are in position.

And the same lines as format=txt. The times in a text export are in UTC.

[02:02:15] SM Desk: Good evening all, this is your five minute call for beginners.
[02:02:18] ASM Stage Left: Stage left copies, all cast are in position.

See Archive and search for the same exports from the screen.

Follow the transcript live​

GET /stream is a server-sent event stream: one event for each finished line, for as long as you keep the connection open. -N stops curl from holding the output back.

curl -sSN \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  "$EARSHOT/api/v1/stream"

Each event is an id: line and a data: line. This one is cut short where the ... is:

id: 7580
data: {"seq":7580,"at":1794794857756,"event":{"type":"utterance_final","data":{"id":"01M7H1R4QFD73MAJTRA8K5X1J6","channel_id":"demo-sm","text":"Good evening all, this is your five minute call for beginners.", ...}}}
  • It carries finished lines only. Drafts, names on lines, alerts and Armed or Safe changes are on the WebSocket (below).
  • It ends when its token is revoked or its role changes. Connect again.

A few lines of Python that print each line as it is finished:

import json
import os
import urllib.request

request = urllib.request.Request(
    os.environ["EARSHOT"] + "/api/v1/stream",
    headers={"Authorization": "Bearer " + os.environ.get("EARSHOT_TOKEN", "")},
)
with urllib.request.urlopen(request) as stream:
    for raw in stream:
        line = raw.decode().strip()
        if line.startswith("data:"):
            event = json.loads(line[5:])["event"]
            if event["type"] == "utterance_final":
                print(event["data"]["channel_id"], event["data"]["text"])

Send a typed line​

Needs Viewer, on a channel that allows typing. The id in the address is the channel's id.

curl -sS \
  -X POST \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"text":"standby cue 12"}' \
  "$EARSHOT/api/v1/channels/01JC8Z4M2Q7K9R3VX5TB6N1WDE/messages"

The reply is the line as stored, with "kind":"typed" and "author" set to your name. Your name comes from the personal link's label, or from the header X-Earshot-Name (up to 40 characters; "Guest" if you send none).

A typed line never fires a phrase automation, however it arrives.

Add a marker​

Needs Operator.

curl -sS \
  -X POST \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"label":"Act 2 start"}' \
  "$EARSHOT/api/v1/markers"
{"id":"01M7H1RSPTFFQE9HHZBQ80456T","session_id":"01M7H1EDP38RJNA0R63AQPMZZP","at":1794794874586,"label":"Act 2 start","author":"Guest"}

Make the show Safe​

Needs Operator.

curl -sS \
  -X PUT \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"armed":false}' \
  "$EARSHOT/api/v1/armed"
{"type":"ok"}

{"armed":true} arms.

danger

Arming lets automations really send cues. A script that arms the show is a script that can fire them. Read Safe and Armed.

  • Arm and Safe from every source (screens, API, OSC) are applied in the order the host receives them. The last one wins.
  • A request that was overtaken by a later one answers 409 ("a later arm/safe command was received first"), unless it asked for the state that now holds.
  • A request the engine does not finish within 2 seconds answers 503. A stuck Arm therefore cannot hold back a Safe for more than about 2 seconds.
  • After a 409 or a 503 on a Safe, read /state and send Safe again if armed is still true.

Test a phrase​

Needs Operator. This is the Test bench: always a dry run, whether the show is Safe or Armed. Nothing is sent.

curl -sS \
  -X POST \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"channel_id":"01JC8Z4M2Q7K9R3VX5TB6N1WDE","text":"go cue twelve"}' \
  "$EARSHOT/api/v1/test-phrase"

channel_id is optional. The reply lists what would fire. From the demo host, whose one automation listens for standby lighting cue {number}, the text "standby lighting cue five" gave:

[
  {
    "id": "01M7H1RSNNBCGY9WGR2K2SFQHH",
    "automation_id": "tour-standby",
    "automation_name": "Standby marker",
    "at": 1794794874549,
    "dry_run": true,
    "trigger": "phrase \"standby lighting cue 5\" on SM Desk",
    "utterance_id": null,
    "results": [
      {"summary": "would add marker \"Standby LX 5\"", "ok": true, "skipped": "dry run: nothing was sent"}
    ]
  }
]

An empty list ([]) means no automation would fire.

Run an automation​

Needs Operator. This is Run now. The id in the address is the automation's id (from /state). Its name or short name does not work here.

curl -sS \
  -X POST \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"vars":{"cue":"12"}}' \
  "$EARSHOT/api/v1/automations/01JC8Z5A7P3D2H9TQ4WZ8F6KCB/trigger"
  • While the show is Safe this is a dry run. The reply has "dry_run": true and each result says "dry run: nothing was sent". While Armed it really sends.
  • vars is optional. Each value you send can be used in the automation's actions as {{var.<name>}}: here, {{var.cue}}. See Variables.
  • It can take up to 2 seconds to answer.
  • Two runs of one automation less than 0.1 seconds apart: the second is refused.
  • An automation limited to named people never fires this way. See Automations limited to people.

Fire a webhook​

An automation whose trigger is A web request has its own address:

POST http://<host>:4780/api/v1/webhooks/<path>
curl -sS \
  -X POST \
  -d 'scene 3' \
  "$EARSHOT/api/v1/webhooks/lights/go"
  • It needs no token, in any access mode. The path is the secret. Whoever has it can fire that automation. Earshot shows the address only once, when you make the trigger. Copy it then. See Triggers and Saved secrets.
  • It still obeys Safe and Armed. While Safe the reply is a dry run.
  • Whatever you send as the body is passed to the automation as text, as {{var.body}}.
  • An unknown path answers 404 ("no automation uses this webhook path") and counts as a wrong guess (see "Limits" below).
  • An automation started by a webhook that fires more than 20 times in 10 seconds is stopped. See When an automation is not running.

The live connection (WebSocket)​

One WebSocket carries everything the screens show live: draft and finished lines, levels, alerts, automation firings, Armed and Safe changes. It also takes commands. It is at:

ws://<host>:4780/api/v1/ws?token=<token>

Messages are JSON text. In outline:

DirectionMessageMeaning
You send{"op":"hello","resume_from":null}Start. resume_from is the last seq you processed, or null the first time.
Host sends{"op":"snapshot","snapshot":{...},"resync":false,"role":"operator","name":"Guest"}Always first: the whole state, as /state gives it.
Host sends{"op":"event","seq":1235,"at":1700000000000,"event":{"type":"utterance_final","data":{...}}}One thing that happened. Keep the seq.
You send{"op":"command","id":7,"command":{"type":"send_typed","data":{"channel_id":"...","text":"copy"}}}Do something. id is yours, to match the reply.
Host sends{"op":"reply","id":7,"ok":true,"reply":{"type":"ok"}}The answer to command 7. Replies can arrive out of order.
You send{"op":"ping"}The host answers {"op":"pong"}.
  • If you reconnect with resume_from set, the host replays what you missed (it keeps the last 5 000 events), then carries on live. If resync is true, too much was missed or the host restarted: throw away what you have and read the history again with /utterances.
  • An utterance_partial with empty text means "remove that draft line".
  • A connection that falls too far behind (1 000 messages waiting) is closed. Connect again.
  • Close code 4401 means your token is no longer accepted: sign in again. 4403 means your role changed: connect again.

Any command can also be sent without a WebSocket, to POST /command:

curl -sS \
  -X POST \
  -H "Authorization: Bearer $EARSHOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type":"set_armed","data":{"armed":false}}' \
  "$EARSHOT/api/v1/command"

The API reference on the host has a short working example in JavaScript and the full list of events and commands.

Limits​

WhatLimit
Wrong guesses from one device (a wrong password, an unknown token, a bad invite code, an unknown webhook path)5, then that device is locked out for 30 seconds, doubling each time up to 15 minutes
WebhooksA burst of 20, refilled at 10 a second, per sender and per path
Password sign-ins and invite claims, all devices together20 at once, and 20 started a second
Failed password sign-ins, all devices togetherAfter 100 in a minute, new password sign-ins are refused for 60 seconds
Connections64 from one device, 192 from all other devices together. A WebSocket or an event stream holds one for its whole life.
WebSocketCommands 16 at a time per connection. A message over 2 MiB closes it.

Every limit answers 429 Too Many Requests with a Retry-After header (in seconds) and:

{"error":{"code":"rate_limited","message":"too many attempts; try again in N s"}}

A token that is already in use keeps working while a device is locked out. Only new sign-ins and unknown tokens are refused. Devices behind one router or one proxy count as one device.

Errors​

Statuserror.codeMeaning
400bad_requestThe body or the query is not valid.
401unauthorizedNo token, or an unknown, expired or revoked one, and the show is not Open.
403forbiddenYour role is too low, or the request came from another website (below).
404not_foundNo such channel, automation, alert, token, code or clip.
409conflictFor example, a later Arm or Safe was received first.
421misdirectedThe address used is not one the host recognises (below).
429rate_limitedA limit or a lockout. Wait Retry-After seconds.
500internalSomething went wrong inside the host.
503unavailableThe engine did not answer in time, or is shutting down.

The address must be one the host recognises​

Earshot refuses any request whose address names a computer it does not know it is. The answer is 421:

{"error":{"code":"misdirected","message":"this server does not answer to that host name"}}

These always work: any IP address, localhost, and the computer's own name (also with .local). Any other name (a venue DNS name, a reverse proxy) is refused until you add it when starting the headless program, with --allow-host NAME. See earshotd.

This is what stops a web page on someone's laptop from reaching Earshot under a made-up name.

Requests from other websites are refused​

There is no cross-site access. A web page that is not Earshot's own cannot change anything: a request that changes something (anything but a read), or a WebSocket, that carries a browser's Origin header from another site is refused with 403 ("cross-origin requests are not allowed"). Scripts and tools that send no Origin header, such as curl, are not affected. Webhooks are the exception: they accept a request from anywhere, because the path is the secret.

Secrets are never returned​

No reply contains a saved password, cloud key, link code, web request header value or webhook path, for any role. An admin gets the marker •••• where one is saved. When you write settings back, send the marker back unchanged to keep the saved value, an empty string to remove it, or a new value to replace it.

Everyone below Admin also gets web addresses in automations cut back to the host name, and shell commands hidden. The show file from GET /show/export is hidden the same way for everyone, admins included. See Saved secrets.

What has been tried​

The read, typed-line, marker, Safe, test-phrase and run examples on this page were run with curl against a demo host on the same computer, with that host's own ids in place of the long example ids. The replies shown are what came back (the ids and times are that run's), apart from the computer's name. The password sign-in and the webhook example were not run. The API has not been tried from another computer on a real network, or with real show-control software. See Limits and known behaviour.
