When an automation does not run

Three different things can keep an automation from doing its job:

  1. It is "not running": Earshot has set it aside and says why. See Not running.
  2. The runaway stop has stopped it because it fired too fast. See The runaway stop.
  3. It is running, but that one call did not fire. See A cue did not fire.

A problem on one automation never stops the others.

When an automation is "not running"​

The Automations list says "1 automation is not running." at the top, with a button:

ButtonWhat it does
Show it (one automation) or Show only these (several)Narrows the list to the automations with a problem.
Show allBack to the whole list.

One automation that is not running. Mock show, not a real show.

The automation itself shows:

  • a red Problem badge beside its name,
  • "Not running" beside its switch,
  • and a line that starts "Not running:" or "Needs fixing:". Read it: it says what to change.

"Not running:" comes from the host: it has set the automation aside. "Needs fixing:" comes from the editor's own checks, for example a field left empty. Open the automation with Edit to see the same messages at the top of the editor.

Run now on an automation that is not running does nothing. The button says "Run now will do nothing: the host is not running this automation. The reason is listed under it.", and the host answers "this automation cannot run: …".

The runaway stop​

If an automation that was started by OSC or a web request (or by the automations they chain) really fires more than 20 times in 10 seconds, Earshot stops that automation.

  • An alert reads "'Name' fired 20 times in 10 seconds and was stopped" and stays on screen until someone acknowledges it.
  • The automation shows the Problem badge with the "Stopped after firing 20 times…" line.
  • The other automations keep working.

To start it again, make the show Safe and then Armed again, or edit the automation. Find the cause before you do, or it will stop again.

What it is for​

It is aimed at loops. The usual one: a console that echoes OSC back into Earshot, so that an automation's own output arrives as its trigger.

What it does not cover​

Started byCovered by the runaway stop?What limits it instead
OSC, or a web request (and the automations they chain)Yes
A spoken phraseNoCooldown. Set it on the automation.
MIDINoOnly the 0.1 second spacing below.
Run now, or another manual startNoThe 0.1 second spacing below.
  • Dry runs are not counted. A loop while the show is Safe sends nothing and trips nothing.
  • Any two firings of one automation from anything other than speech are at least 0.1 seconds apart. A closer one is refused.
  • A firing that Earshot refuses still uses up that automation's cooldown.
A MIDI feedback loop is not stopped

An automation whose MIDI output comes back in as its own trigger is limited only by the 0.1 second spacing: about ten firings a second, until you make the show Safe. Check that a MIDI device does not echo before you arm.

A cue did not fire​

Go down this list in order. Most answers are on one row of the Activity log, so open that first. The long version, with every other kind of fault, is in Troubleshooting.

  1. Is the show Armed? In Safe nothing is sent. A row reading Would have fired Name with Dry run means it matched and Safe held it back. See Safe and Armed.
  2. Was the show Armed when the words began? Look for "heard before the show was armed" or "Safe was pressed after this was said". Arm first, then speak.
  3. Is the automation on, with no problem? Check the Enabled switch, and look for a Problem badge or "1 automation is not running." above.
  4. Did Earshot hear it correctly? Read the line in the Feed. Then use Use last heard line on the Test bench and see whether the automation would fire. It matches whole words, after numbers are turned into digits.
  5. Was it refused for a number reason? Look for did not fire: the number may be incomplete: …. See How Earshot hears numbers, and say the number a different way.
  6. Cooldown. Activity says cooling down (N ms left). A new automation's cooldown is 2 seconds.
  7. A condition. Activity says condition not met: …. Check channel, group, time and flag conditions, and Where to listen.
  8. The runaway stop. Look for the alert "fired 20 times in 10 seconds and was stopped".
  9. Was the line typed? Typed lines never fire phrase automations. Neither do translations, or lines from another Earshot computer.
  10. Is it limited to people? It fires only when Earshot is very sure who spoke, which is rare on a noisy line. See Automations limited to people.
  11. Fire on Draft or Final. On Final text it waits for the settled line, and a channel that is Behind is slow.
  12. Did it fire, but the destination did not get it? Activity shows the send. A row marked Failed says why when you open it. Check the destination's host, port and protocol (Manage destinations in the editor), and whether the device is on the network. A TCP destination that is down is retried, and the sends skipped meanwhile are logged.

If the row says fired and is not marked Failed, Earshot sent it. Look at the receiving device next: its OSC input setting, its port, and the address it expects.
